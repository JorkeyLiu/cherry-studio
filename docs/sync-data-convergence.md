## 1. Context and problem

The implemented operation log converges covered topic, message, and message-block shapes between devices that share history, but the product question it does not answer is data convergence: what a newly paired device receives, what two devices with pre-existing independent data become, how a third device joins later, how long history survives retention, how divergence is detected and repaired, and when the UI may claim devices hold the same user data.

Without locked convergence semantics, each of those questions invites a local shortcut — raw database copy, one-directional overwrite, absence treated as deletion, cursor reset on missing history, or push/pull retry presented as reconciliation — that would silently lose user data or falsely claim synchronization. This ADR locks the target convergence semantics as the design authority for complete synchronization of the syncable personal-data domain.

| **SYNC-DATA-033** | Parent-scoped order frame as the wire merge field for complete sync (target-only, code-less): user-visible `message`/`block` order belongs to the complete-synchronization domain and must not be permanently excluded from sync. | **SYNC-DATA-034** | Frame authority boundary (target-only, code-less): a frame decides only the relative order among currently alive members of the same parent; it never creates, deletes, reparents, or resets parent identity, and never overwrites entity content/fields. Membership and deletion remain governed by entity existence plus `op`/tombstone semantics (`SYNC-DATA-005`/`SYNC-DATA-006` plus §6). A frame that would imply a different parent, resurrect a tombstoned member, or invent an entity is out-of-authority and its out-of-authority members are not materialized (see `SYNC-DATA-035`). | **Locked** |
| **SYNC-DATA-035** | Concurrent frame merge with validity filtering, membership-clock-gated completeness, and deterministic retention — normative algorithm (target-only, code-less; closes F-02): concurrent frames for the same parent resolve by the existing `timestamp+operationId` total-order LWW (the same total order governing field clocks; no new ordering key introduced). Winner determination uses that total order only; payload order or receipt order does not decide. The winning frame's `ordered child IDs` are then filtered to the set of currently alive, same-parent, known children: duplicates are de-duplicated by first appearance (first occurrence retains semantic position; later duplicates ignored), deleted/tombstoned children, children whose parent identity differs per current membership, and unknown child IDs are not materialized and do not resurrect. Logical `parent-membership clock` governs coverage (normative): each child carries a logical `parent-membership clock (timestamp, operationId)` sharing the same total order as existing clocks; it is established at child creation and, only if a future explicitly governed `reparent` operation is accepted, updated by that reparent; ordinary content/field edits never change it. The winning frame's `frame clock` is the coverage cutoff. If any effective alive same-parent child has `membershipClock <= frameClock` yet is absent from the winner's ordered list, the frame is **incomplete** — receiver must reject/repair fail-closed per `SYNC-DATA-015`/`SYNC-DATA-039`, not silently append. Children with `membershipClock > frameClock` (concurrent or later arrivals relative to the winner's snapshot) that are alive and same-parent must be retained and appended deterministically by `membershipClock` ascending then `child ID` lexicographically. Any required membership clock missing or not comparable (not totally ordered with the frame clock) causes fail-closed (`400` on publish where applicable, otherwise blocked/repair-required per `SYNC-DATA-015`). Silent member loss to preserve winner-frame exactness is prohibited. `parent-membership clock` is a new logical contract state not yet implemented; it does not lock table/column/op/JSON spelling per `SYNC-DATA-040`, and current entity clocks must not substitute for it (see living doc). | **Locked** |
| **SYNC-DATA-036** | Atomic frame apply with persistent winning frame, fixed-point re-evaluation, deterministic dense materialization, baseline/incremental equivalence, and atomic transaction boundary (target-only, code-less; closes F-03/F-04): a receiver applies a parent's order frame atomically with the `SYNC-DATA-035` validity filtering, membership-clock-gated completeness check, and deterministic append (by `membershipClock` then `childId`), then materializes the resulting logical order into local dense `sortOrder 0..n-1` following the filtered winner plus deterministic append sequence. The receiver persistently stores per-parent winning-frame state. Whenever the winning frame for a parent changes, or any relevant child `existence` / `parent-membership clock or parent identity` / `tombstone` state changes, the receiver re-runs the same `SYNC-DATA-035` filtering / completeness / append / materialization algorithm until a deterministic fixed point is reached, guaranteeing arrival-order independence. Baseline application and incremental operation replay that deliver the same set of entity states plus the same winning frames reach the same logical order; dense `sortOrder` values are local projection/query authority only and carry no additional merge meaning beyond the frame-derived sequence. The SQLite governance in [sqlite-migration.md](./sqlite-migration.md) is not rewritten: local `sortOrder` remains authoritative for local queries/projection while wire truth is the frame per `SYNC-DATA-038`. **Transaction boundary (normative):** one visible commit must atomically cover all affected state for its scope: entity/tombstone/`parent-membership` merge, per-parent winning-frame state, the complete dense `sortOrder 0..n-1` for every affected parent (source and destination parents for a `reparent`; single parent for create/delete/frame-only), and the corresponding replay `applied`/`cursor` state. `reparent` is atomic across both sides. If the commit cannot complete all of the above, the change stays pending/invisible with a full rollback — no partial projection is committed. | **Locked** |
| **SYNC-DATA-037** | Baseline logical-payload order-frame coverage and structural-operation issuance rule (target-only, code-less): the baseline logical payload (`SYNC-DATA-004`/`SYNC-DATA-027`) must carry order frames for every parent within the versioned inventory. Incremental delivery of order is via frames (or an explicitly governed equivalent atomic group that yields the same frame semantics). Any future structural operation that changes user-visible `message`/`block` order — including `reorder`, `insert-at`, `branch`/`clone`/`paste`/`select-answer` or equivalent that reorders visible children — must issue the corresponding order frame(s) (or the governed equivalent atomic group) before a device may claim complete convergence for its domain. | **SYNC-DATA-038** | Wire inventory exclusion of per-row `sortOrder` with local projection authority preserved (target-only, code-less): per-row `message.sortOrder` and `message_block.sortOrder` are excluded from the wire logical payload as entity fields and from the wire field-clock inventory; they are not transmitted as row properties and carry no per-field clock on the wire. ## 4. Definitions

- **Syncable personal-data domain**: the explicitly versioned set of user data covered by the §10 inventory for a claimed sync scope. Only this domain is subject to complete-synchronization claims.
- **Complete synchronization**: after convergence, each paired device holds the same logical user data for the claimed domain, within the locked merge/tombstone/aggregate rules — not merely the same operation count or cursor.
- **Logical baseline**: an allowlisted, schema-versioned, device-independent capture of syncable state at a per-channel watermark, usable for bootstrap and repair. Generated client-side from Main SQLite authority. Never a raw database file.
- **Current effective baseline**: the single per-channel baseline blob plus schema/inventory-version, digest, and watermark metadata the relay durably persists and serves for bootstrap. A new publish replaces it atomically only when gated by `SYNC-DATA-023` and with in-flight bootstraps protected by `SYNC-DATA-024`; prior-version physical reclamation is deferred.
- **Availability copy vs content truth**: device-held Main SQLite state is content truth and rebuild source; the relay-persisted baseline is an offline-bootstrap availability copy that carries no adjudication power.
- **Operation watermark N**: the per-channel sequence position up to which a baseline claims to incorporate channel operations. Replay resumes at N+1 with gap repair per SYNC-DATA-007 and the three-segment boundary per SYNC-DATA-021.
- **Tombstone/delete evidence**: explicit versioned deletion state for an entity. The only convergence input that removes state; absence of an entity in a baseline or stream is never deletion evidence.
- **Parent-membership clock** (logical, `SYNC-DATA-035`–`SYNC-DATA-036`): per-child logical clock `(timestamp, operationId)` sharing the same total order as existing clocks, proving current parent membership. Established at child creation; only an explicitly governed accepted `reparent` updates it; ordinary content edits never change it. Winning `frame clock` is the coverage cutoff (`membershipClock <= frameClock` must be listed or frame is incomplete; `membershipClock > frameClock` is deterministic append by `membershipClock` then `childId`; missing/incomparable is fail-closed). This is a new logical contract state with no implementation yet; table/column/op/JSON spelling is not locked per `SYNC-DATA-040`; current entity clocks are not this clock.
- **Manifest/digest**: a comparable summary of meaningful held state (entity set and versions per the claimed domain), used to detect divergence and scope repair. Transport counters alone are not a manifest. Wire baseline integrity uses the locked public digest contract `jcs-sha256-v1` per `SYNC-DATA-032` (I-JSON-compatible logical payload — entities plus clocks plus tombstones plus **order frames** plus manifest — RFC 8785 JCS UTF-8 canonical bytes, SHA-256 lowercase 64-hex, fail-closed inputs, versioned-logical-payload-only scope with atomic envelope binding; frame JSON key spelling not locked per `SYNC-DATA-040`).
- **Targeted repair**: redelivery of the missing/divergent baseline partition or operation range identified by manifest comparison.
- **Data-convergence status**: the device's truthful claim about its converged state for a claimed domain (§8), independent of service connection and pairing membership.

## 5. Baseline and bootstrap (normative)

1. A baseline declares its schema version, its claimed inventory scope, and its per-channel watermark N. A receiver validates all three before applying; anything unvalidatable is rejected fail-closed per SYNC-DATA-015.
2. The baseline payload contains only allowlisted syncable fields (§10). Credentials, device-local paths, caches/FTS artifacts, and transient/UI-derived state are never baseline content, even when colocated with syncable rows in local storage.
3. Baseline origin is client-side and device-independent: a publishing device captures its baseline from its own Main SQLite authority; the relay never generates, merges, or adjudicates baseline business content (SYNC-DATA-019). The relay validates the protocol envelope and durably persists, per channel, the single current effective baseline blob plus schema/inventory-version, digest, and watermark metadata; a new publish replaces the effective baseline atomically only when it passes the SYNC-DATA-023 serialization/monotonic/coverage gate, and in-flight bootstraps stay protected per SYNC-DATA-024 (SYNC-DATA-019, SYNC-DATA-022–SYNC-DATA-024).
4. Bootstrap applies in watermark order: apply the baseline at N, then replay N+1 onward. Concurrent writes above N are part of the converged result; the handoff must prove no gap between what the baseline incorporated and where replay resumed (SYNC-DATA-007). The watermark handoff follows the three-segment boundary (SYNC-DATA-021): publish snapshot-boundary proof, relay atomic publish with N+1-onward retention, and receiver single-transaction merge with cursor=N or whole rollback.
5. A joining device may bootstrap from the relay-persisted current effective baseline even when all prior devices are offline (SYNC-DATA-020). Online-device temporary supply is not the main path; this ADR introduces no presence tracking and no baseline source election.
6. Applying a baseline merges with — never overwrites — local pre-pair data and pending outbox intent (SYNC-DATA-008, §6). A device with unsent local operations keeps them pending through bootstrap and still requires their acknowledgement; the baseline does not acknowledge them.
7. Parent/child aggregates apply under §7 completeness/ordering or atomic group semantics. Partial aggregates never become durable user-visible shells.
8. Baseline release uses the single-stage client-declared publish model only (SYNC-DATA-025): one publish operation carrying the `SYNC-DATA-027` envelope categories. There is no relay-issued fence, token, or prepare handshake to implement, request, or wait for.
9. The publisher proves the `SYNC-DATA-026` barrier before publishing: quiescence, drained and confirmed pre-barrier outbox, continuous pull to an empty page with no unresolved gap, then one in-barrier SQLite snapshot capturing logical baseline plus clocks plus tombstones plus channel binding plus cursor N plus outbox=0 plus digest. The barrier releases after publish success or failure. Barrier/attestation orchestration is not implemented in current code.
10. The relay applies the `SYNC-DATA-028` validation boundary and the `SYNC-DATA-029` state machine: `empty` versus `current baseline`, atomic replace on success, idempotent `200` retry only on full match with the current effective baseline (channel binding, N, digest scheme/version, digest, canonical logical payload), stale `409` for a replaced-candidate retry with no permanent cross-replacement fingerprint, `409` on same-N divergence or below-current watermark/overwrite conflict, `400` on structure/version/digest invalid, existing-`401` service auth plus `403` device-credential/membership refusal, `413` oversize, `500` store failure, all error bodies as `{error}`. Empty fetch returns `404` `{error:'baseline-not-found'}` as a legitimate empty state, not a routing error. Digest checks follow `SYNC-DATA-032` (`jcs-sha256-v1` recompute; match proves byte-identity only).
11. Fetch serves the current envelope only to authenticated channel members; the client then pulls with cursor=N for N+1 onward (SYNC-DATA-030). SSE stays hint-only without the blob; a dedicated baseline event stays deferred per SYNC-DATA-031.

## 6. Merge, ordering, and deletion (normative)

1. **Identity**: stable entity IDs identify the same logical entity on every device. Re-issuing identity at apply time (duplicating an entity because it arrived from another device) violates SYNC-DATA-006.
2. **Field merge**: updates carry intentional changed fields; independent fields of the same entity merge across devices. Merge behavior for the currently validated shapes stays compatible with the existing timestamp-then-operationId LWW for the current protocol version; a future versioned ordering decision may supersede the tie-break only through its own governed decision, never by silent drift. Per-row `message.sortOrder` / `message_block.sortOrder` are not wire fields per `SYNC-DATA-038`; field merge never touches member ordering.
3. **Deletion wins by evidence, not by absence**: only explicit versioned tombstone/delete evidence removes state. A baseline or stream that omits an entity states nothing about that entity. First-pairing union (SYNC-DATA-005) therefore keeps both sides' entities unless a tombstone says otherwise.
4. **Late descendants stay contained**: a child arriving after its parent's tombstone is suppressed and must not resurrect the parent. This extends the existing parent-tombstone containment to baseline/bootstrap delivery: a baseline that carries a tombstoned parent plus a descendant the tombstone already covers applies the tombstone outcome, not the descendant.
5. **Outbox preservation**: local pending intent participates in merge as unsent local state, not as already-converged state. Conflict ordering applies when that intent replays against converged state; bootstrap never pre-resolves it by dropping it.
6. **Parent-scoped order frames — the ordering contract** (`SYNC-DATA-033`–`SYNC-DATA-036`, normative): user-visible order for inventory-covered `message`/`block` members is governed solely by parent-scoped order frames as defined in `SYNC-DATA-033`. Each `topic` carries one `topic → message` frame, each `message` carries one `message → block` frame; each frame contains parent identity, ordered child IDs in user-visible order, `frame clock (timestamp, operationId)`, and frame version. Frames are strictly closed per version (`SYNC-DATA-039`): unknown fields or unknown frame version fail closed. See §6A for full boundary, merge, and materialization rules. Topic ordering is not introduced by this unit: if the current product has no per-topic visible-order field analogous to `message.sortOrder`/`block.sortOrder`, no topic order frame or field is introduced here; only `message`/`block` order is locked. Any future topic ordering requires its own governed decision.

## 6A. Parent-scoped order frame — boundary, merge, and materialization (normative)

Parent-scoped order frames (`SYNC-DATA-033`–`SYNC-DATA-036`) govern user-visible sequence without governing membership or content:

1. **Authority boundary** (`SYNC-DATA-034`): a frame decides only the relative order among currently alive members of the same parent. It never creates, deletes, reparents, or resets parent identity, and never overwrites entity content/fields. Membership and deletion remain governed by entity existence plus `op`/tombstone semantics (`SYNC-DATA-005`/`SYNC-DATA-006` plus §6 items 3–4). A frame that would imply a different parent, resurrect a tombstoned member, or invent an entity is out-of-authority and its out-of-authority members are not materialized.
2. **Concurrent merge — normative algorithm with logical parent-membership clock** (`SYNC-DATA-035`, closes F-02): concurrent frames for the same parent resolve by the existing `timestamp+operationId` total-order LWW — the same total order governing field clocks; no new ordering key is introduced. Winner determination uses that total order only; payload order or receipt order does not decide. The winning frame's `ordered child IDs` are then filtered: duplicates are de-duplicated by first appearance (first occurrence retains semantic position; later duplicates ignored), deleted/tombstoned children, children whose parent identity differs per current membership, and unknown child IDs are not materialized and do not resurrect. **Logical `parent-membership clock` (normative, new logical contract state, no implementation yet):** each child carries a logical `parent-membership clock (timestamp, operationId)` sharing the same total order as existing clocks; it is established at child creation and, only if a future explicitly governed `reparent` operation is accepted, updated by that reparent; ordinary content/field edits never change it. The winning frame's `frame clock` is the coverage cutoff. If any effective alive same-parent child has `membershipClock <= frameClock` yet is absent from the winner's ordered list, the frame is **incomplete** — receiver must reject/repair fail-closed per `SYNC-DATA-015`/`SYNC-DATA-039`, not silently append. Children with `membershipClock > frameClock` (concurrent or later arrivals relative to the winner's snapshot) that are alive and same-parent must be retained and appended deterministically by `membershipClock` ascending then `child ID` lexicographically. Any required membership clock missing or not comparable (not totally ordered with the frame clock) causes fail-closed (`400` on publish where applicable, otherwise blocked/repair-required per `SYNC-DATA-015`). Silent member loss to preserve winner-frame exactness is prohibited. Current entity clocks must not substitute for `parent-membership clock`; implementation may not reuse them as the membership clock without an explicit governed revision.
3. **Atomic apply with persistent winning frame, fixed-point re-evaluation, dense materialization, baseline/incremental equivalence, and atomic transaction boundary** (`SYNC-DATA-036`, closes F-03/F-04): a receiver persistently stores per-parent winning-frame state. It applies a parent's order frame atomically with the `SYNC-DATA-035` validity filtering, membership-clock-gated completeness check, and deterministic append (by `membershipClock` then `childId`), then materializes the resulting logical order into local dense `sortOrder 0..n-1` following the filtered winner plus deterministic append sequence. Whenever the winning frame for a parent changes, or any relevant child `existence` / `parent-membership clock or parent identity` / `tombstone` state changes, the receiver re-runs the same `SYNC-DATA-035` filtering / completeness / append / materialization algorithm until a deterministic fixed point is reached, guaranteeing arrival-order independence. Baseline application and incremental operation replay that deliver the same set of entity states plus the same winning frames reach the same logical order; dense `sortOrder` values are local projection/query authority only and carry no additional merge meaning beyond the frame-derived sequence. The SQLite governance in [sqlite-migration.md](./sqlite-migration.md) is not rewritten: local `sortOrder` remains authoritative for local queries/projection while wire truth is the frame per `SYNC-DATA-038`. Per-row `sortOrder` is excluded from the wire logical payload as an entity field and from the wire field-clock inventory; until frames are implemented, local `sortOrder` stays local-only and unsynced, and no partial wire `sortOrder` merge is permitted (`SYNC-DATA-038`). **Transaction boundary (normative, F-04):** one visible commit must atomically cover all affected state for its scope: entity/tombstone/`parent-membership` merge, per-parent winning-frame state, the complete dense `sortOrder 0..n-1` for every affected parent (source and destination parents for a `reparent`; single parent for create/delete/frame-only), and the corresponding replay `applied`/`cursor` state. `reparent` is atomic across both sides. If the commit cannot complete all of the above, the change stays pending/invisible with a full rollback — no partial projection is committed.
4. **Strictly closed per version** (`SYNC-DATA-039`): every versioned wire artifact including order frames has a fixed key set, fixed `required` vs `nullable` rules, and fixed allowed-value constraints. Unknown fields, unknown frame or schema/inventory versions, or unknown envelope categories cause fail-closed rejection (`SYNC-DATA-015`; `400` on publish where applicable, otherwise blocked/repair-required). Silently ignoring unknown fields or versions for forward compatibility is prohibited; forward compatibility requires a new explicitly versioned inventory/schema revision. `parent-membership clock` participates in this strictly closed inventory when versioned.
5. **Not locked here** (`SYNC-DATA-040`): specific operation names, endpoint paths, HTTP verb spellings, `packages/shared` TypeScript types, SQLite tables/columns, `parent-membership clock` storage mapping, and wire frame payload JSON spelling/key names (including digest canonicalization key spelling except as governed by RFC 8785 JCS) are not locked by this ADR. `parent-membership clock` is a new logical contract state with no implementation yet; its table/column/op/JSON spelling is not locked here. No code, migration, or endpoint is authorized here; any mapping to those artifacts requires a future explicitly activated step conforming to the locked semantics above.

## 7. Aggregate completeness (normative)

Aggregates with parent/child references (topics with messages, messages with blocks/segments/branches where the inventory covers them) converge as coherent units:

1. Either the full reference closure arrives (completeness with reference-preserving order), or the group applies atomically, or the incomplete aggregate remains pending/invisible until replay or repair completes it.
2. Ordering-only changes are not convergence inputs under the pre-`SYNC-DATA-033` baseline: before parent-scoped order frames, reordering without content change carries no merge meaning. After `SYNC-DATA-033`–`SYNC-DATA-037`, structural operations that change user-visible `message`/`block` order must issue order frames (or the governed equivalent atomic group) per `SYNC-DATA-037`; ordering changes without a frame do not converge and no complete-convergence claim extends over them.
3. Malformed or unvalidatable aggregate members fail closed per SYNC-DATA-015 without blocking unrelated aggregates beyond what cursor semantics require — and the blockage itself is surfaced as blocked/repair-required, never as convergence.
4. Baseline logical-payload order-frame coverage (`SYNC-DATA-037`, normative): the baseline logical payload (per `SYNC-DATA-004`/`SYNC-DATA-027`) must carry order frames for every parent within the versioned inventory. Incremental delivery of order is via frames (or an explicitly governed equivalent atomic group that yields the same frame semantics). Any future structural operation that changes user-visible `message`/`block` order — including `reorder`, `insert-at`, `branch`/`clone`/`paste`/`select-answer` or equivalent that reorders visible children — must issue the corresponding order frame(s) (or the governed equivalent atomic group) before a device may claim complete convergence for its domain. The current implementation has no frame issuance for such structural operations; this gap is explicitly recorded and no complete-convergence claim extends over reordered state until the frame path exists. `sortOrder` is not a wire entity field (`SYNC-DATA-038`); only frames carry ordering on the wire.

## 8. Reconciliation and convergence status (normative)

1. Reconciliation starts from manifest/digest comparison over the claimed domain, scopes the divergence (missing entities, divergent versions, incomplete aggregates, uncovered prefix), and repairs through targeted redelivery. Push/pull retry without comparison and scoped repair is liveness, not reconciliation (SYNC-DATA-012).
2. History-unavailable (compacted prefix without a covering baseline, or a cursor pointing at unavailable operations) routes to bootstrap/repair under §5. Silent cursor reset — advancing past unavailable history and claiming convergence — is prohibited (SYNC-DATA-011).
3. Convergence status is per claimed domain and independent of `SYNC-CC-*` service/pairing status. At minimum it distinguishes: `Synced`, `Converging` (catch-up/repair in progress), `Partial` (claimed domain subset only), `Unsupported` (domain outside the versioned inventory), `Blocked` (version incompatibility or unresolvable failure), and `Repair required` (divergence or history-unavailable awaiting bootstrap/repair).
4. `Synced` holds only when baseline completeness, operation catch-up, zero unresolved apply failures, and successful consistency verification all hold for the claimed domain. Verification means a manifest/digest comparison confirming the same logical state, not equal cursor values alone.
5. Status transitions never delete or roll back user data to reach a cleaner state. Repair adds or corrects through governed inputs (baseline, replay, tombstones); it never removes local state except through explicit tombstone/delete evidence.

## 9. Retention and compaction (normative)

1. The compacted prefix must be covered by a valid recoverable baseline plus the tombstone/deletion evidence needed to preserve deletion outcomes for entities removed within the prefix. "Covered" is proven by recoverability: a device bootstrapping from retained state reaches the same logical outcome for live and deleted entities as replay from the uncompacted log would have produced. A baseline publish that cannot provide that coverage for the prefix it would compact is rejected per SYNC-DATA-023 and changes nothing effective.
2. Until that proof exists for a prefix, the prefix is retained. While a baseline is the channel's current effective baseline, its required prefix is never trimmed: the continuous log from N+1 onward is retained (SYNC-DATA-021). Replacement additionally preserves the N+1 replay/repair path of any successfully issued baseline until its bootstrap completes or explicitly fails, via retained baseline/log/delete evidence or an equivalent recoverable mechanism (SYNC-DATA-024). With no compaction implemented, full log retention is the minimal path satisfying that protection; it does not lock a long-term never-compact constraint (SYNC-DATA-031). Retention duration, storage location, endpoint path strings, HTTP verb spellings, chunking/streaming, size thresholds, compression, capacity thresholds, retained history physical counts, prior-version physical reclamation mechanics, lease/ack endpoints, timeouts, retained physical old-baseline counts, SSE event names, and reaping mechanics are deferred implementation choices (SYNC-DATA-017, SYNC-DATA-022, SYNC-DATA-024, SYNC-DATA-031), but the coverage precondition is not deferrable.
3. A device encountering history it cannot recover routes to bootstrap/repair and reports blocked/repair-required. It never advances past the gap silently.

## 10. Syncable-data inventory requirement (normative)

1. A versioned inventory must exist before any full-sync claim, classifying at minimum: (a) required user data that complete synchronization covers; (b) optional configuration governed separately with its own scope and default behavior; (c) device-local exclusions that never enter the channel (credentials, device-local paths, caches/FTS, transient/UI-derived state). For `SYNC-DATA-033`–`SYNC-DATA-039`, inventory versions additionally enumerate the set of parents whose order frames are required.
2. The currently validated topic/message/partial message-block scope is a subset of that inventory, not complete-product sync. Claims for the current scope stay bounded to the living reference's evidence; broader claims wait for explicit contract coverage. For ordering, per-row `message.sortOrder` / `message_block.sortOrder` are excluded from the wire field inventory per `SYNC-DATA-038`; ordering lives in parent-scoped frames per `SYNC-DATA-033`. Topic ordering is not introduced by this unit: if the current product has no per-topic visible-order field analogous to `message.sortOrder`/`block.sortOrder`, no topic order frame or field is introduced here; only `message`/`block` order is locked. Any future topic ordering requires its own governed decision.
3. Structured content, ordering/segments/branches, attachments and attachment bytes each require explicit contract coverage (shape, reference integrity with §7 aggregates, transport, and verification) before full-sync claims extend to them. Exclusion from a claim is explicit inventory scope, not silent omission. All per-version wire artifacts including order frames are strictly closed: fixed key set, fixed `required` vs `nullable` rules, fixed allowed-value constraints; unknown fields or unknown versions fail closed per `SYNC-DATA-039` (`SYNC-DATA-015`), never silently ignored.
4. Wire inventory exclusion of per-row `sortOrder` (`SYNC-DATA-038`, normative): per-row `message.sortOrder` and `message_block.sortOrder` are excluded from the wire logical payload as entity fields and from the wire field-clock inventory; they are not transmitted as row properties and carry no per-field clock on the wire. Local SQLite dense `sortOrder 0..n-1` remains local projection/query authority materialized from frames per `SYNC-DATA-036` and does not rewrite [sqlite-migration.md](./sqlite-migration.md) storage or migration governance.

## 11. Disconnect, Unpair, and version consequences

- **Disconnect** (per `SYNC-CC-*` service attachment) changes reachability only. It preserves local data, pending outbox intent, cursors, and convergence status inputs; on reconnect, catch-up and reconciliation resume from pinned positions.
- **Unpair** (per `SYNC-CC-*` channel membership) stops future channel convergence for the unpaired device. It preserves all local data on every affected device, including data that arrived through sync, and performs no rollback, revert, or deletion of already synchronized state (SYNC-DATA-014).
- **Version incompatibility** (unknown baseline/operation/manifest/inventory version, unknown order-frame version, unknown wire fields, or a peer outside the compatible protocol version) fails closed per SYNC-DATA-015/`SYNC-DATA-039`: pin, retain, surface truthfully, and route to upgrade or repair. Downgrade-by-discard and compatibility-by-ignoring-unknown-fields are not permitted by this ADR; any such rule would require its own governed decision. For order frames, an unknown frame version or unknown field inside a strictly closed frame causes fail-closed rejection (`400` on publish where applicable, otherwise blocked/repair-required per `SYNC-DATA-039`), never silent ignore.

## 13. Rejected alternatives (stable decisions)

- **Physical database copy as sync — rejected** (SYNC-DATA-003, SYNC-DATA-004). Copying `chat.db` across devices would transport device-local paths, credentials-adjacent material, caches/FTS artifacts, and schema-instance coupling, and would overwrite rather than merge. Baselines are logical and allowlisted; the continuous mechanism remains the operation log.
- **Absence as deletion — rejected** (SYNC-DATA-005). Treating a missing entity as a delete would turn every partial baseline, filtered scope, or in-flight aggregate into data loss. Only explicit versioned tombstones delete.
- **Snapshot/log gap handoff — rejected** (SYNC-DATA-007). Resuming the stream above the baseline watermark without proving coverage loses concurrent writes. The handoff must prove N+1-onward delivery or repair.
- **Baseline application as overwrite or implicit acknowledgement — rejected** (SYNC-DATA-008). Overwrite loses pre-pair data; implicit acknowledgement fabricates durability for unsent intent.
- **Relay merge/adjudication of baseline content — rejected** (SYNC-DATA-019). The relay validates the protocol envelope and saves/distributes; business truth is decided by per-device Main SQLite under these semantics.
- **Locally observed cursor as watermark proof — rejected** (SYNC-DATA-021). Baseline content and the relay-continuously-persist-confirmed watermark N must share one provable snapshot boundary.
- **Prefix trimming under an effective baseline — rejected** (SYNC-DATA-021, SYNC-DATA-022). While a baseline is effective, the continuous log from N+1 onward is retained.
- **Unserialized or coverage-less baseline replacement — rejected** (SYNC-DATA-023). Concurrent publishes without per-channel serialization, watermarks without relay-continuously-persist-confirmed proof, below-current watermarks violating the `N >= current` monotonic floor, and candidates that cannot cover the compacted prefix plus required tombstone/delete evidence are not convergence; the relay rejects such publishes with the effective baseline unchanged (below-current is `409`; coverage is an additional gate, never a substitute).
- **Severing an in-flight bootstrap's N+1 path — rejected** (SYNC-DATA-024). Replacing the effective baseline must not remove the continuous replay/repair path of a successfully issued baseline before its bootstrap completes or explicitly fails; retention or an equivalent recoverable mechanism preserves it. Full log retention is the minimal path when no compaction exists, not a locked never-compact promise (SYNC-DATA-031).
- **Per-entity `sortOrder` as wire merge field — rejected** (SYNC-DATA-033, SYNC-DATA-038). Per-row `message.sortOrder`/`message_block.sortOrder` as a wire entity field with per-field clock merge is not the convergence mechanism; ordering converges via parent-scoped order frames. Per-row `sortOrder` is excluded from wire entity field/field-clock inventory and carries no merge meaning; local dense `sortOrder 0..n-1` is materialization only.
- **Order frame as membership/content authority — rejected** (SYNC-DATA-034). A frame never creates, deletes, reparents, or resets parent identity, and never overwrites entity content/fields; membership and deletion remain governed by entity/tombstone/op semantics.
- **Silent member loss on concurrent order divergence — rejected** (SYNC-DATA-035). Concurrent frames resolve by `timestamp+operationId` LWW and validity filtering; any alive same-parent child absent from the winning frame — including concurrently inserted members — must be retained and deterministically appended (recommended: entity clock then child ID), or fail closed if deterministic inputs are missing; silently dropping members to preserve winner-frame exactness is not convergence.
- **Non-atomic or divergent baseline vs incremental order materialization — rejected** (SYNC-DATA-036). A parent's order frame applies atomically and materializes to dense `sortOrder 0..n-1`; baseline and incremental replay delivering the same entity states plus winning frames must reach the same logical order.
- **Ordering excluded from complete sync or baseline without frames — rejected** (SYNC-DATA-033, SYNC-DATA-037). User-visible `message`/`block` order belongs to the complete-synchronization domain and is not permanently excludable; the baseline logical payload must carry order frames for every inventory-within parent and structural reorder/insert-at/branch/clone/paste/select-answer operations must issue frames (or equivalent atomic group) before a complete-convergence claim.
- **Silently ignoring unknown wire fields/versions for compatibility — rejected** (SYNC-DATA-039). Every versioned wire artifact including order frames is strictly closed per version; unknown fields, unknown frame or schema/inventory versions, or unknown envelope categories cause fail-closed rejection, never silent ignore.
- **Locking frame wire spelling/storage mapping in this ADR — not selected** (SYNC-DATA-040). Operation names, endpoint paths/verbs, `packages/shared` types, SQLite tables/columns, and wire frame JSON spelling are not locked here and require a future explicitly activated step.
- **Relay-issued fence/token/prepare handshake — rejected** (SYNC-DATA-025). Baseline release needs no pre-publish grant; adding one would add coordination without changing the serialized gate outcome.
- **Online-device supply as the main bootstrap path and presence/source election — rejected** (SYNC-DATA-020). The main offline path is the relay-persisted availability copy; no presence tracking and no source election are introduced.
- **Partial aggregate shells — rejected** (SYNC-DATA-009). A durably visible parent without its children (or child without its parent) presents state the user never created.
- **Silent cursor reset on missing history — rejected** (SYNC-DATA-011). Advancing past unavailable operations manufactures convergence while abandoning data and deletion outcomes.
- **Push/pull retry as reconciliation — rejected** (SYNC-DATA-012). Retry without comparison cannot detect divergence it never looks at.
- **Connection/pairing status as convergence proof — rejected** (SYNC-DATA-013). A paired and connected device with unapplied operations, pending bootstrap gaps, or unverified state is not `Synced`.

## 14. Security and privacy

- Baselines, operations, manifests, and repair traffic carry only allowlisted syncable fields (§10). Credentials, device-local paths, and transient/UI-derived state are excluded at capture, not redacted at display.
- Secrets (registration credentials, tokens, keys) are never baseline, manifest, log, or evidence content. Evidence and logs carry counts/statuses/digests only, never content, credentials, paths, or raw sizes.
- Main SQLite remains the local chat authority (SYNC-DATA-002); the relay remains store-and-forward/coordination and never owns chat truth, including when it persists and serves baselines. Relay compromise or loss affects availability and coordination, never the definition of converged truth — recovery comes from device-held state under these semantics.
- Transport security, E2EE, and attachment-byte protection are deferred implementation choices and are not decided here.

## 15. Conformance requirements

An implementation conforms to this ADR only when its observed behavior satisfies, at minimum:

1. Paired devices with pre-existing independent data reach the bidirectional union outcome: both sides' entities survive absent explicit tombstones; absence alone deletes nothing.
2. A joining device bootstraps from a watermark-bound baseline plus N+1-onward replay with no gap loss under concurrent writes, while its local pre-pair data and pending outbox intent survive bootstrap unacknowledged. The publish snapshot boundary, relay atomic publish with N+1-onward retention, and receiver single-transaction merge with cursor=N or whole rollback hold per SYNC-DATA-021; publish additionally passes the SYNC-DATA-023 serialization/monotonic/coverage gate and in-flight bootstraps stay protected per SYNC-DATA-024.
3. Same-entity independent fields merge; same-field collisions resolve deterministically compatibly with the current timestamp-then-operationId LWW for the current protocol version; tombstoned parents contain late descendants without resurrection. Per-row `sortOrder` is not a wire field per `SYNC-DATA-038`; ordering converges via parent-scoped frames per `SYNC-DATA-033`–`SYNC-DATA-036`.
4. Parent-scoped order frames converge correctly per `SYNC-DATA-033`–`SYNC-DATA-036`: each inventory-covered parent carries a frame with parent identity + ordered child IDs + `frame clock (timestamp, operationId)` + version; frames are strictly closed per version (`SYNC-DATA-039`); a frame decides only relative order among same-parent alive members and never creates/deletes/reparents or overwrites content (`SYNC-DATA-034`); concurrent frames resolve by `timestamp+operationId` LWW with validity filtering (dedup by first appearance; deleted/different-parent/unknown children not materialized) and deterministic retention append for alive children absent from the winner (recommended: entity clock then child ID; missing total-order inputs fail closed) per `SYNC-DATA-035`; receivers apply frames atomically and materialize to local dense `sortOrder 0..n-1` with baseline/incremental equivalence per `SYNC-DATA-036`. Topic ordering is not introduced by this unit: only `message`/`block` order is governed; per-row `sortOrder` is excluded from wire inventory per `SYNC-DATA-038`.
5. Aggregates never rest as durable partial user-visible shells; incomplete aggregates stay pending/invisible until completed by replay or repair. After `SYNC-DATA-037`, structural `message`/`block` order changes without a corresponding frame (or governed equivalent atomic group) do not converge and no complete-convergence claim extends over them.
6. Baseline logical payload carries order frames for every inventory-within parent and structural reorder/insert-at/branch/clone/paste/select-answer operations issue frames per `SYNC-DATA-037`; per-row `sortOrder` is not a wire field per `SYNC-DATA-038`; baseline and incremental order results are equivalent per `SYNC-DATA-036`.
7. Retention/compaction keeps recoverability for live and deleted entities; history-unavailable routes to bootstrap/repair with a truthful blocked/repair-required state and never a silent cursor advance. Each channel holds at most one current effective baseline with gated atomic replacement per SYNC-DATA-023 and in-flight protection per SYNC-DATA-024; full log retention is the minimal protection path with no compaction, not a never-compact lock (SYNC-DATA-031); prior-version physical reclamation, lease/ack endpoints, timeouts, retained physical old-baseline counts, and GC mechanics stay deferred.
8. Reconciliation demonstrates manifest/digest comparison with scoped targeted repair; push/pull retry alone does not satisfy this item. Order divergence is detected via frame comparison under the same manifest/digest regime.
9. `Synced` is claimed per domain only with baseline completeness, operation catch-up, no unresolved apply failures, and successful consistency verification; all other states are reported truthfully. After `SYNC-DATA-037`, `Synced` additionally requires order-frame completeness for the claimed domain.
10. Disconnect and Unpair preserve local data; Unpair stops future convergence without rolling back already synchronized state.
11. Version incompatibility and unresolvable failures behave fail-closed: pinned cursor, retained state, truthful status, no fabricated convergence. For order frames, unknown fields, unknown frame version, or missing deterministic retention inputs cause fail-closed per `SYNC-DATA-039`/`SYNC-DATA-035`/`SYNC-DATA-015`.
12. Baselines are client-generated device-independent state; the relay persists and serves the per-channel current effective baseline plus schema/digest/watermark metadata with envelope validation only, and a joining device may bootstrap from it while all prior devices are offline, with no presence/source election. The baseline logical payload includes order frames per `SYNC-DATA-037` and per-row `sortOrder` remains excluded per `SYNC-DATA-038`.
13. Publish/fetch follows the single-stage client-declared wire contract: publisher barrier/snapshot per SYNC-DATA-026, envelope categories per SYNC-DATA-027 (now including order frames where inventory covers ordering per `SYNC-DATA-037`), relay validation per SYNC-DATA-028 (including `SYNC-DATA-023` monotonic floor `N >= current` in non-`empty` state and `SYNC-DATA-032` `jcs-sha256-v1` recompute over the frame-inclusive logical payload), state machine plus `200` (full current-match only; replaced-candidate retry is stale `409` without permanent fingerprint)/`400`/`401`/`403`/`404` (`{error:'baseline-not-found'}` on empty)/`409` (same-N divergence, below-current watermark, or overwrite conflict)/`413`/`500` with `{error}` bodies per SYNC-DATA-029, public digest `jcs-sha256-v1` with versioned-logical-payload-only scope, fail-closed canonicalization, recompute-proves-byte-identity-only, and atomic envelope binding per SYNC-DATA-032 (canonical bytes now deterministically include order frames), and member-only fetch with cursor=N then N+1 pull plus hint-only SSE per SYNC-DATA-030. No fence/token/prepare handshake exists per SYNC-DATA-025. Wire frame payload JSON spelling and operation names stay deferred per `SYNC-DATA-040`.

Conformance is a property of observed behavior against the statements above. This ADR does not prescribe test shape, evidence form, or implementation sequence.

## 16. Deferred items and consequences

- Endpoint path strings, HTTP verb spellings, chunking/streaming, size thresholds, compression, capacity thresholds, retained history physical counts, prior-version physical reclamation mechanics, exact retention duration, attachment transport, SSE event names, and E2EE: deferred (SYNC-DATA-017, SYNC-DATA-022, SYNC-DATA-031). Digest scheme/canonical bytes are locked per `SYNC-DATA-032` and are not deferred. Parent-scoped order-frame wire logical semantics (frame composition, LWW + validity filtering + deterministic append, atomic dense materialization, baseline/incremental equivalence, baseline frame coverage, per-row `sortOrder` exclusion, per-version strictly closed) are locked per `SYNC-DATA-033`–`SYNC-DATA-039`; operation names, endpoint paths/verbs, `packages/shared` types, SQLite tables/columns, and wire frame payload JSON spelling remain deferred per `SYNC-DATA-040`. Lease/ack endpoints, timeouts, retained physical old-baseline counts, and GC/reclamation mechanics additionally stay deferred under SYNC-DATA-024 and SYNC-DATA-031. Consequence: no baseline, bootstrap, reconciliation, or retention work starts until its own explicitly activated step defines these within the locked invariants. Operation semantics and status codes are already locked per SYNC-DATA-025/`SYNC-DATA-028`–`SYNC-DATA-030` and are not deferred.
- Syncable-data inventory content (exact entity/field lists and versions): required by SYNC-DATA-010 but its content lives in its own governed artifact/step. For ordering, inventory versions now additionally enumerate the parent set whose order frames are required and the wire field inventory explicitly excludes per-row `message.sortOrder`/`message_block.sortOrder` per `SYNC-DATA-038`; this unit locks only `message`/`block` order — topic ordering is not introduced (if the current product has no per-topic visible-order field analogous to `message.sortOrder`/`block.sortOrder`, no topic frame is introduced). Consequence: until the inventory and the per-domain contracts it demands exist, full-sync claims stay unmade and scope claims stay bounded to validated shapes.
- Conflict-recovery UX and row-level conflict visibility: deferred. Consequence: deterministic ordering resolves same-field collisions without a dedicated user recovery experience until a later decision designs one.
- Channel garbage collection, multi-group/merge, and credential recovery remain deferred under `SYNC-CC-*`; snapshot/backfill history they touch additionally requires this ADR's retention/repair preconditions.

## 17. ADR change policy

- **Status**: Approved and fixed. This ADR is the authoritative owner of target data-convergence semantics (`SYNC-DATA-*`). It stays unchanged while the design is unchanged.
- **Living state lives elsewhere**: current implementation, evidence, gaps, and next step belong exclusively to [multi-device-sync.md](./multi-device-sync.md), which references this ADR as target governance and must not duplicate its decision tables.
- **Design change requires a new decision**: this ADR changes only by explicit user-approved amendment, or is marked superseded by a named successor ADR that states what it replaces. The superseded ADR is retained for audit and no longer authoritative.
- **Evidence never silently modifies decisions**: validation runs, implementation findings, and new evidence are recorded in the living reference; they do not alter this ADR's decisions without an amendment or superseding ADR.
- [sync-architecture-selection.md](./sync-architecture-selection.md) stays a conditional fallback reference; it is unaffected by this ADR except for a routing pointer.
- **No implementation authorization flows from this ADR.** No baseline, bootstrap, reconciliation, retention, inventory, status, migration, IPC, or code change is authorized by citing it. Citing this ADR as proof that the target convergence model is implemented is false.
